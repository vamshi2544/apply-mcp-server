Machine-readable APIs and MCP

What "machine-readable API" means, how it differs from the APIs we run today, and which approach to use when exposing Apply products to AI agents through MCP.

01The short answer

In one sentence

A machine-readable API is not a different API. It is our existing API plus a complete, precise description that software can read and act on without a person explaining it. The industry standard for that description is the OpenAPI Specification.

Our APIs already return JSON, so the data is machine-readable. Every Apply API, including prequal, also already has a Swagger (OpenAPI) spec published through Apigee, so we are not starting from zero. What is usually incomplete is the description: what each field means, which values are possible, what each error means, which calls must happen in which order, and which calls are safe to retry. Developers fill those gaps by reading Confluence or asking a colleague. A program cannot. An AI agent is the extreme case, because it has no colleagues, no Confluence, and no memory of how the API behaved last week.

For MCP the two are not alternatives. The machine-readable description is the foundation. MCP tools are built on top of it, either generated from it automatically or written by hand with it as the reference.

03Who the "machine" is

Three kinds of software read an API description. Each needs a little more than the one before.

ReaderWhat it does with the descriptionWhat it needs
Tools: code generators, SDKs, mock serversGenerates client classes, stubs, documentation sitesCorrect paths, types, required fields
Platforms: gateways, test suites, cataloguesValidates requests, runs contract tests, lists APIs for discoveryPlus accurate errors, security schemes, versions
AI agents: through MCP or similarDecides whether, when and how to call the API, then explains the result to a personPlus meaning: what codes signify, when to use each operation, what must happen first, what is safe to retry

Why the AI case is different: a code generator that meets a vague field generates a vague field. An AI agent that meets a vague field guesses. In credit acquisition a guess can mean telling an applicant they were approved when they were only prequalified, or retrying an acceptance and creating a duplicate application.

04The standards involved

Each piece is an open standard. None is specific to one vendor.

StandardWhat it describesRelevance to us
OpenAPI Specification (3.1, 3.2)An HTTP API: paths, operations, parameters, request and response bodies, errors, securityThe core of "machine-readable". We already use it through SwaggerHub; the question is completeness.
JSON SchemaThe shape and rules of JSON data. OpenAPI 3.1 and later use it directly.Types, enums, formats, required fields. MCP tool inputs are also JSON Schema.
RFC 9457 Problem DetailsA standard JSON format for HTTP errors: type, title, status, detailOne error shape across Apply APIs, so agents and clients handle errors the same way everywhere.
Arazzo (OpenAPI Initiative)Multi-step workflows across API calls, such as offers then accept then statusMakes our call sequence machine-readable instead of tribal knowledge.
RFC 9727 api-catalogA well-known URI (/.well-known/api-catalog) listing an organisation's APIsDiscovery: lets tools and agents find which APIs exist. Optional, later.
MCPHow AI agents discover and call toolsThe delivery channel to agents. Sits on top of the APIs and their descriptions.

05Maturity levels

A practical scale for answering "where are our APIs today?" Score each Apply API.

L0
Undescribed
No spec. Knowledge in Confluence and people.
L1
Partial spec common
A spec exists but is stale or covers only paths and types. Errors, enums and examples missing or wrong.
L2
Complete and accurate common
Every operation, field, enum, error and security scheme is present, with examples. The spec is validated against the running API in CI, so it cannot drift.
L3
Agent-ready needed for MCP
Each operation says what it is for and when to use it. Every code is explained. Errors use one standard shape. Idempotency, retry safety, consent and prerequisites are stated. Operation ids are clear verbs (getPrequalOffers, not post1).
L4
Discoverable and workflow-aware
Listed in an API catalogue. Multi-step flows described with Arazzo. Versioning and deprecation policy published.

Where we likely are: all Apply APIs have Swagger specs in Apigee, so they are at least L1 and probably L2 for structure. The gap to L3 is meaning: code explanations, purpose, prerequisites, idempotency and error semantics. Also check the spec version: Swagger 2.0 specs may need converting to OpenAPI 3.x, which most MCP generators expect. Conversion is a tooling step, not a rewrite.

Auto-generating good MCP tools needs L3. A curated MCP server can work with L2, because the missing meaning is written into the tool layer by hand, but L3 still makes that work faster and safer.

06Example: the prequal offers operation

The same endpoint described at L1 and at L3. The API does not change; only the description does.

openapi.yamlL1 · partial
/v1/prequal/offers:
  post:
    operationId: postOffers
    requestBody:
      content:
        application/json:
          schema:
            $ref: '#/components/schemas/Req'
    responses:
      '200':
        description: OK
        content:
          application/json:
            schema:
              properties:
                prequalId: { type: string }
                decisionCd: { type: string }
                offers: { type: array }
      '400':
        description: Bad request
openapi.yamlL3 · agent-ready
/v1/prequal/offers:
  post:
    operationId: getPrequalOffers
    summary: Check credit card prequalification
    description: >
      Soft credit inquiry; does not affect the
      applicant's score. First step of a prequal.
      Requires the applicant's explicit consent.
      Not a final credit decision.
    responses:
      '200':
        content:
          application/json:
            schema:
              properties:
                decisionCd:
                  type: string
                  enum: [A1, D1, R1]
                  description: >
                    A1 qualified, offers returned.
                    D1 not qualified.
                    R1 identity or address not
                    confirmed; ask applicant to
                    check details and retry.
            examples: { qualified: …, declined: … }
      '400':
        content:
          application/problem+json:   # RFC 9457
            schema: { $ref: Problem }

The L1 version tells a program that decisionCd is a string. The L3 version tells it what the three possible values mean and what to do about each. An agent working from the L1 version would have to guess what A1 means.

The workflow, also machine-readable (Arazzo, L4)

prequal.arazzo.yaml (sketch)L4
workflows:
  - workflowId: prequalifyAndApply
    steps:
      - stepId: getOffers
        operationId: getPrequalOffers
        successCriteria: [ { condition: $response.body.decisionCd == 'A1' } ]
      - stepId: accept
        operationId: acceptPrequalOffer
        parameters: [ { name: prequalId, value: $steps.getOffers.outputs.prequalId } ]
      - stepId: status
        operationId: getApplicationStatus

Apigee can already do route A

Google has added MCP support to Apigee, currently in preview (access through the Apigee or Google Cloud account team). You deploy an "MCP proxy" with an OpenAPI spec attached, and Apigee serves the spec's operations as MCP tools. No code and no separate MCP server. The MCP proxy can be bundled in an API product, so the usual Apigee quota, identity and access policies decide which agents can list and call which tools, and the proxy is registered in Apigee API hub as a tool catalogue.

What Apigee MCP gives usWhat it does not change
MCP endpoint with no code, from our existing specsTool quality still equals spec quality, so specs must reach L3
Same Apigee policies, API products and analytics we already runNo business logic: it cannot require consent, confirmation, or prevent a second acceptance
Tool catalogue in API hubInternal codes and full payloads reach the agent unless the spec and proxy handle them

Check before promising it: the feature is in preview, and documentation refers to Apigee on Google Cloud and Apigee hybrid. Confirm which Apigee edition we run and whether the preview is enabled for us. Our curated server works regardless, and can itself sit behind Apigee as a normal proxy.

08Which route, operation by operation

Ask these questions about each API operation in order. The first "yes" decides.

1. Does it change state or create something? (accept offer, submit application, update details)
Yes → Curate. Needs confirmation, idempotency key and audit in code.
No → question 2
2. Does it involve consent, disclosures or a credit inquiry? (prequal offers)
Yes → Curate. A consent check must be enforced, not just described.
No → question 3
3. Does the response contain internal codes or more data than an agent should see?
Yes, and the spec can't explain them → Curate (translate and trim).
No, or the spec explains them → question 4
4. Is the spec at L3 for this operation?
Yes → Generate. A simple read with a good spec is a good candidate (application status lookup).
No → fix the spec first, then generate

Applied to prequal

OperationDecisionReason
Get offersCurateCredit inquiry with consent; codes need translation
Accept offerCurateIrreversible, idempotency, confirmation
Application statusGenerate later (curated today)Read only; possible once the spec explains status codes

09Recommendation

What is best

Keep the APIs. Raise their OpenAPI specs to agent-ready (L3). Use a hybrid route to MCP: generate simple read-only tools from the specs, and hand-build tools for anything that changes state, touches consent, or creates an application.

Why

  • Spec quality benefits everyone, not only AI: generated clients, contract tests, gateway validation, partner onboarding, one source of truth.
  • Generation alone is not safe for credit actions. A generator copies the API's shape. It cannot require consent, prevent a second acceptance, or stop an agent retrying with a new idempotency key.
  • Curation alone does not scale to every Apply API. Generating reads keeps effort proportional to risk.
  • No backend rewrites, so no regression risk for web, mobile and partner channels.
  • Fits Apigee today, Kong later. Apigee's MCP proxy (preview) or Kong's conversion mode covers route A; either gateway can front the curated server in route B as a normal proxy.

What to say

"Machine-readable is about the description, not the API. All our APIs already have Swagger specs in Apigee. We keep the APIs, enrich those specs until they are agent-ready, and then generate MCP tools for simple reads while hand-building tools for anything that creates an application or involves consent. Our prequal proof of concept already shows the hand-built path working."

10Spec audit checklist (L3)

Use per API. Every unchecked item is a gap to fix.

  • Spec in Apigee / SwaggerHub matches production
  • Spec is OpenAPI 3.x (convert from Swagger 2.0 if needed)
  • Spec validated against the running API in CI
  • Every operation has a clear operationId verb
  • Every operation has a summary and a "when to use" description
  • Every request and response field has a description
  • Every coded field is an enum with each value explained
  • Required fields, formats and limits are declared
  • Every error status is documented with its codes
  • Errors use RFC 9457 Problem Details (or one agreed shape)
  • Idempotency documented: header, replay behaviour, 409 meaning
  • Retry safety stated per operation
  • Prerequisites stated (consent, prior call, auth scope)
  • Examples for success and each main failure
  • Security scheme declared (OAuth scopes or API key)
  • PII fields marked (for example an x-pii: true extension)
  • Version and deprecation policy stated

11Questions you may get

  1. Are our APIs machine-readable today?Yes for structure: every Apply API, including prequal, has a Swagger spec in Apigee (L1–L2). Not yet agent-ready (L3): what codes mean, prerequisites, idempotency and error meanings live mostly outside the spec. The work is enriching specs we already have, not creating them.
  2. We have Apigee. Can Apigee expose our APIs as MCP?Yes, Apigee has MCP support in preview: an MCP proxy serves a spec's operations as tools, governed by API products and the usual policies. It is the gateway version of route A, so it suits simple reads with good specs. For accept and other consent-bearing actions we still need the curated tool layer, which can sit behind Apigee as a normal proxy. Confirm edition and preview access with the account team.
  3. Do we need to build new APIs?No. The work is improving the descriptions, plus a thin tool layer for MCP.
  4. Can Kong convert our APIs into MCP tools automatically?Yes, its AI MCP Proxy plugin has a conversion mode that builds tools from OpenAPI. It works well for simple reads with good specs. It is not enough for accepting offers, because it cannot enforce consent, confirmation or idempotency rules, and it passes internal codes through unchanged.
  5. Then why not curate everything?Effort. Curating every endpoint across all Apply products is slow. Generating reads from good specs lets the team spend hand-built effort only where risk is high.
  6. What is the biggest risk?A poor spec produces an agent that guesses. In credit that can mean misstating a decision or duplicating an application. So spec quality is a control, not documentation overhead.
  7. Is this an industry standard or our own idea?Standard. OpenAPI and JSON Schema for description, RFC 9457 for errors, Arazzo for workflows, RFC 9727 for discovery, MCP for agent access.
  8. How long does it take?Spec uplift is per API and depends on the gap found in the audit. The curated prequal POC exists already. A sensible first milestone is one API at L3 plus one generated read-only tool.
  9. Who owns it?Each API team owns its spec; the L3 checklist becomes part of the definition of done for API changes. The MCP layer is owned centrally as one service.
  10. Does this help beyond AI?Yes: generated clients, contract testing, gateway request validation, faster partner onboarding, fewer "how does this field work" questions.

12Proposed next steps

  1. AuditScore every Apply API L0–L4 using the checklist in section 10.
  2. Reference APILift the prequal spec to L3 as the model for other teams.
  3. StandardAgree the L3 checklist and one error format as the definition of done for API changes.
  4. Generation pilotAsk the Apigee account team for MCP preview access, then expose one read-only operation (application status) through an Apigee MCP proxy from an L3 spec and compare it with the curated tool.
  5. Curated layerContinue the curated MCP server for state-changing and consent-bearing flows.
  6. GatewayFront the curated MCP server with Apigee (or Kong if production moves) and decide the caller authentication model and API products for agents.

13Glossary and sources

Machine-readable API
An API whose behaviour and meaning are fully described in a format software can read, usually OpenAPI.
Agent-ready
Machine-readable plus meaning: purpose, code meanings, prerequisites, retry safety. Level L3 here.
OpenAPI
Standard document format describing HTTP APIs. Swagger is the older name and a tool family.
JSON Schema
Standard for describing the shape and rules of JSON data.
Problem Details
RFC 9457 standard error format for HTTP APIs.
Arazzo
OpenAPI Initiative standard for describing multi-step API workflows.
API catalogue
A list of an organisation's APIs; RFC 9727 defines a standard location for it.
MCP
Model Context Protocol: how AI agents discover and call tools.
Curated tool
An MCP tool written by hand over an API, with business rules in code.
Generated tool
An MCP tool produced automatically from an OpenAPI operation.

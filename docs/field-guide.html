Apply APIs · MCP enablement · Capability 1: Prequal

Exposing prequalification to AI agents through MCP

An end-to-end guide for taking the existing prequal APIs (offers, accept, status), turning them into MCP tools, and running them locally before anything goes near production.

Audience: API lead new to MCPStack: Java · Spring Boot · ApigeeScope: local first

01What MCP is

The Model Context Protocol (MCP) is an open standard that lets an AI application discover and call external capabilities in a uniform way. Before MCP, every AI product needed custom integration code for every API. With MCP, you build one server, and any MCP-compatible client (Claude Desktop, Claude Code, VS Code Copilot, an internal agent platform) can use it.

The closest familiar idea is this: MCP is to AI agents what OpenAPI plus an API gateway is to applications. It describes what is available and defines how to call it. The difference is that the consumer is a language model that reads descriptions and decides on its own which tool to call and with what arguments.

The three roles

Host
Claude Desktop, an agent app

The application the person uses. It contains the model and decides when to call tools.

Client
Built into the host

Holds one connection to one MCP server. You do not write this; the host provides it.

Server
What you build

Publishes tools and executes them. Yours will call the prequal APIs through Apigee.

What a server can publish

  • Tools: actions the model can call, such as prequal_get_offers. This is 95% of your work.
  • Resources: read-only data the host can load as context, such as product terms or a disclosure document.
  • Prompts: reusable, parameterised instructions a user can pick, such as "Run a prequal for a customer".

Transports

  • stdio: the host starts your server as a local process and talks over standard input and output. Simplest option, local only.
  • Streamable HTTP: your server runs as a web service with one MCP endpoint (for example /mcp). This is what you deploy to PCF and put behind Apigee so that "anyone can reach it".
For your case: since the target is a shared service, build with Streamable HTTP from the start, even locally. It runs on localhost:8080 exactly like any Spring Boot app.

02How a call works on the wire

MCP messages are JSON-RPC 2.0. Seeing the four messages below removes most of the mystery.

Step 1. Handshake

The client sends initialize with the protocol version it supports. Your server replies with its name, version, and capabilities (for example, "I have tools"). The SDK handles this for you.

Step 2. Discovery: the model reads your catalogue

CLIENT → SERVER
{ "jsonrpc": "2.0", "id": 2, "method": "tools/list" }
SERVER → CLIENT
{ "jsonrpc": "2.0", "id": 2, "result": { "tools": [{
  "name": "prequal_get_offers",
  "description": "Check whether an applicant prequalifies for a credit card using a soft credit inquiry...",
  "inputSchema": { "type": "object", "properties": { ... }, "required": [ ... ] }
}]}}

The name, description, and inputSchema are copied into the model's context. This is the only thing the model knows about your API. It never sees your Swagger, your Confluence page, or your code.

Step 3. Invocation: the model decides to call

CLIENT → SERVER
{ "jsonrpc": "2.0", "id": 3, "method": "tools/call",
  "params": { "name": "prequal_get_offers",
              "arguments": { "first_name": "Jane", "last_name": "Doe", ... } } }

Step 4. Result: your server answers

SERVER → CLIENT
{ "jsonrpc": "2.0", "id": 3, "result": {
  "content": [{ "type": "text", "text": "Applicant prequalified for 2 offers..." }],
  "structuredContent": { "decision": "QUALIFIED", "offers": [ ... ] },
  "isError": false } }

Note that a business failure (applicant not qualified, invalid ZIP) is returned as a normal result, with isError: true when the call itself failed. The model reads the message and explains it or corrects its input. A JSON-RPC protocol error is reserved for things like an unknown tool name.

03Use the APIs as-is, or make them machine-readable?

This is the main design question. It has two parts that are often confused.

Recommendation

Do not change the existing APIs. Build a thin, agent-facing tool layer on top of them inside the MCP server. Make sure each API has an accurate OpenAPI specification, because that machine-readable contract is what the tool layer is built and tested against.

Part 1. "Machine-readable" as in OpenAPI

Your APIs are already machine-readable to programs if they have a correct OpenAPI (Swagger) specification in SwaggerHub. That spec matters here for three reasons: it is the source for generating request and response classes in the MCP server, several tools can generate a first draft of MCP tools from it, and it is how you validate that your tool layer still matches the backend after API changes. If the spec is stale or incomplete, fixing it is step zero.

Part 2. "Agent-readable": the part that really matters

A spec written for developers is not automatically usable by a model. A developer reads the Confluence page, asks a colleague, and learns that decisionCd = "A2" means "approved with conditions". A model has none of that. Exposing each endpoint one-to-one as a tool usually produces these problems:

  • Internal codes in responses (A2, RC014) that the model will guess at or misreport to the user.
  • Headers and plumbing (client IDs, correlation IDs, channel codes, Apigee keys) exposed as tool arguments. The model should never see or invent these.
  • Large nested responses that waste the model's context and bury the two fields that matter.
  • Unstated sequencing: the model does not know it must call offers before accept, or that accept is irreversible.
  • Unsafe retries: if a timeout occurs on accept, nothing tells the model whether calling again creates a duplicate application.

The three options compared

ApproachEffortAgent accuracySafety on writesBackend change
A. Wrap each endpoint 1:1
Pass requests and responses through unchanged		LowPoorWeakNone
B. Auto-generate from OpenAPI

Option C gives option D's accuracy without touching the APIs that the web, mobile, and partner channels depend on. Option B is a useful way to get a first draft of tool schemas quickly, which you then curate into option C.

05Prequal tool design

Three tools, one per business step. The field names below are illustrative; replace them with your real contract.

prequal_get_offersSoft inquiry · creates a record

Checks whether an applicant prequalifies for credit card offers using a soft credit inquiry, which does not affect the applicant's credit score. Use this first in any prequalification. Before calling, confirm the applicant has agreed to a soft credit check and set consent_soft_inquiry to true.

Inputs
first_name, last_name, address_line1, city, state, zip_code, date_of_birth, ssn_last4, annual_income, consent_soft_inquiry
Returns
decision (QUALIFIED, NOT_QUALIFIED, NEEDS_MORE_INFO), prequal_id, offers[ offer_id, product_name, credit_limit, purchase_apr, expires_at ], reason, next_step
Retry rule
Safe to retry on timeout with the same inputs.
prequal_accept_offerIrreversible · state change

Accepts one prequalified offer and starts a credit card application. This cannot be undone. Only call this after the applicant has seen the offer terms and explicitly said they want this specific offer. Generate one idempotency key per acceptance and reuse the same key if you retry.

Inputs
prequal_id, offer_id, idempotency_key (UUID), applicant_confirmed (must be true)
Returns
application_id, status, next_step ("Call prequal_get_application_status")
Retry rule
Retry only with the same idempotency_key. A different key for the same offer returns a conflict, not a second application.
prequal_get_application_statusRead only

Returns the current status of an application created by prequal_accept_offer. Use this when the applicant asks about progress. If the status is PENDING, wait before checking again; do not call repeatedly in a loop.

Inputs
application_id
Returns
status (PENDING, APPROVED, DECLINED, NEEDS_VERIFICATION), reason, next_step
Retry rule
Always safe.

Make the mock deterministic so every path is testable: for example, income below 20,000 returns D1, ZIP 00000 returns R1, and application IDs ending in 9 stay pending.

Idempotency mapped to tool results

Your existing idempotency rules carry straight into the accept tool. The point is that the model is told what each result means, so it does not create a duplicate application after a timeout.

SituationBackendWhat the tool tells the model
Same key, already processedPrevious response replayedAccepted earlier. Here is the application_id. Do not retry.
Same key, still in progress202Processing. Check status with the application tool, do not call accept again.
Same key, previous attempt failedReprocessedNormal result.
Same key, different payload409isError. Key reused for a different offer. Generate a new key only if the applicant chose a different offer.
Offer expired4xxisError. Offer expired; run prequal_get_offers again.

Rules for writing descriptions

  • Say what the tool does, when to use it, what to do before it, and what comes after.
  • Write for a model with zero Synchrony context. No internal acronyms without expansion.
  • Put formats and limits in the schema (pattern, enum, minimum), and the business meaning in the description.
  • Use tool annotations: readOnlyHint on status, destructiveHint and idempotentHint on accept. Hosts use these to decide when to ask the user for approval.
  • Prefix tool names with the product (prequal_) so the catalogue stays clear when other apply products are added.

06Safety and compliance

A credit product exposed to agents raises questions that a normal API does not. Settle these before going beyond local mocks.

Personal data

  • Everything a tool returns enters the model's context and may be stored by the host. Return the minimum. Never echo SSN, full DOB, or full income back in results.
  • Mask PII in MCP server logs exactly as you do in the APIs. Log the tool name, correlation ID, duration, and outcome; not the arguments.
  • Confirm with InfoSec which hosts and models are approved to receive applicant PII. This decides whether a public host can be used at all, or only an internally hosted model.

Consent and confirmation

  • Soft inquiry consent: require an explicit consent_soft_inquiry: true argument and reject the call if it is missing. Ask Compliance whether the required disclosure text must be shown verbatim; if so, publish it as an MCP resource and tell the tool to present it.
  • Accept: require applicant_confirmed: true, mark the tool destructive, and keep a server-side audit record of who confirmed and when. Newer MCP clients also support elicitation, where the server asks the user directly for confirmation; support varies by host, so do not rely on it alone yet.

Credentials and access

  • Apigee keys and client secrets live only in the MCP server's environment (PCF service binding or env vars). They are never tool arguments.
  • Locally, stdio or localhost HTTP needs no caller authentication. Once deployed, the MCP endpoint itself must be protected. The MCP specification defines OAuth 2.1 for HTTP servers; in practice, put the endpoint behind Apigee or your SSO provider and decide whether calls run as a service identity or on behalf of the signed-in employee.

Prompt injection

Treat the model as an untrusted caller. Text from any source the agent reads can try to make it call your tools. Every rule that matters (consent, offer ownership, one acceptance per prequal, input validation) must be enforced in server code, not only described in tool text. Descriptions guide a well-behaved model; code stops a misled one.

07Build it locally

Five phases. Each one ends with something you can demo. Expand a phase for detail.

Phase 0Learn the protocol with a toy½ day

Before writing Java, see MCP work end to end with the official Python SDK. Twenty lines, mocked data, no Apigee.

toy_server.py
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("prequal-toy")

@mcp.tool()
def prequal_get_offers(first_name: str, zip_code: str, annual_income: int) -> dict:
    """Check whether an applicant prequalifies for credit card offers
    using a soft credit inquiry. Use this first in any prequalification."""
    if annual_income < 20000:
        return {"decision": "NOT_QUALIFIED", "reason": "Income below minimum"}
    return {"decision": "QUALIFIED", "prequal_id": "PQ-1001",
            "offers": [{"offer_id": "OF-1", "product_name": "Cashback Card",

if __name__ == "__main__":
    mcp.run()

Phase 1Design the contract on paper1–2 days
  1. Export the OpenAPI specs for offers, accept, and status from SwaggerHub. Check they match production behaviour.
  2. For each endpoint, list every request field and decide: model provides it, server fills it, or drop it.
  3. List every response code and reason code. Write the plain-language translation and the next step for each.
  4. Write the three tool descriptions and JSON schemas. Review them with one developer who has never seen the API; if they cannot use the tool from the description alone, neither can the model.
  5. Write ten test conversations (see section 09) before writing code.
Exit check: a one-page tool contract reviewed by your team, plus open questions sent to Compliance and InfoSec.
Phase 2Spring AI MCP server with mocks2–3 days

Create a Spring Boot app with the Spring AI MCP server starter for Spring MVC. Tools are ordinary Spring bean methods with an annotation. Exact property names and annotation options change between Spring AI versions, so confirm against the version available in your internal repository.

pom.xml
<dependency>
  <groupId>org.springframework.ai</groupId>
  <artifactId>spring-ai-starter-mcp-server-webmvc</artifactId>
</dependency>
<!-- version managed by spring-ai-bom -->
PrequalTools.java
@Service
public class PrequalTools {

  private final PrequalClient client;   // adapter: mock now, Apigee later

  @Tool(name = "prequal_get_offers", description = """
      Check whether an applicant prequalifies for credit card offers using a
      soft credit inquiry, which does not affect their credit score. Use this
      first in any prequalification. Before calling, confirm the applicant
      agreed to a soft credit check and set consent_soft_inquiry to true.""")
  public OffersResult getOffers(OffersRequest request) {
    if (!request.consentSoftInquiry()) {
      throw new IllegalArgumentException(
          "Applicant consent to a soft credit inquiry is required.");
    }
    return OffersMapper.toResult(client.getOffers(OffersMapper.toApi(request)));
  }

  // prequal_accept_offer and prequal_get_application_status follow the same pattern
}

@Configuration
class McpConfig {
  @Bean
  ToolCallbackProvider prequalToolProvider(PrequalTools tools) {
    return MethodToolCallbackProvider.builder().toolObjects(tools).build();
  }
}

Phase 3Connect to a lower environment2–4 days
  1. Register the MCP server as a developer app in Apigee for the lower environment. Store the key in env vars.
  2. Generate REST client classes from the OpenAPI specs, or write a small RestClient adapter.
  3. Set timeouts shorter than the host's tool timeout. Retry reads only; never auto-retry accept.

Prerequisites

  • A current version of the GitHub Copilot plugin for IntelliJ.
  • Agent mode in Copilot Chat. MCP tools are only available in Agent mode, not in Ask or Edit mode.

  2. Open Copilot Chat and switch the mode dropdown to Agent.
  3. Click the tools icon, then Add MCP Tools. This opens mcp.json.
  4. Add your server and save:
mcp.json (Copilot for JetBrains)

  "servers": {
    "apply-prequal": {
      "url": "http://localhost:8080/mcp"
    }
  }

  1. Open the tools icon again. You should see prequal_get_offers, prequal_accept_offer, and prequal_get_application_status with your descriptions.
  2. Prompt it: "I want to check if I prequalify for a credit card." Copilot asks for permission before each tool call; approve and watch the flow.

Data note: Copilot sends tool results to GitHub-hosted models. Keep to mock data until InfoSec confirms otherwise.

09Test and evaluate

Unit tests prove the code works. Conversation tests prove the model uses the tools correctly. You need both.

Tools

  • MCP Inspector (npx @modelcontextprotocol/inspector): browser UI to list and call tools by hand and view raw messages. Use it constantly.
  • JUnit: test each tool method and the mappers directly, including every error code translation.
  • Conversation scripts: a fixed set of user prompts run against a real model, with the tool calls checked.

10Gateways: Apigee today, Kong possibly in production

A gateway can sit in two places in an MCP design. Kong can play either role, and it can also generate MCP tools itself.

The two gateway positions

MCP

Protects the MCP endpoint
MCP
MCP Server
Your tool layer
REST
Gateway B
Fronts the APIs (Apigee today)
  • Gateway B already exists: Apigee in front of the prequal APIs. If production moves the APIs to Kong, only the adapter configuration changes (base URL and credential type).
  • Gateway A is new. Once "anyone" can reach the MCP server, something must authenticate callers, limit rates, control which callers see which tools, and log usage. That is where Kong's MCP features are aimed.

What Kong offers for MCP

Kong Gateway 3.12 and later include an AI MCP Proxy plugin. It requires the AI Gateway Enterprise licence. It works in these modes:

ModeWhat it doesFit for us
Passthrough-listenerProxies MCP traffic to an existing MCP server and adds metrics.Gateway A in front of our Spring server. Server code unchanged.
Conversion-listenerConverts REST API paths into MCP tools from the OpenAPI schema and serves them as an MCP endpoint.Equivalent to option B in section 03. No server code, but no custom logic either.
Conversion-onlyConverts API paths to tools without serving them, for use with a listener.Building block for aggregation.
ListenerAggregates tools from several conversion-only plugins into one MCP endpoint.One catalogue across products, if conversion is used.

Caller authentication uses standard Kong plugins (key auth, OIDC). From version 3.13, Kong can also allow or deny individual tools per consumer or consumer group.

Should Kong replace our MCP server?

Kong's conversion mode is attractive because it removes code. For prequal it is not enough on its own, for these reasons:

  • The consent check, the applicant_confirmed rule, and the idempotency guidance for accept are logic, not mapping. A generated tool cannot enforce them.
  • Generated descriptions come from the OpenAPI text, which is written for developers. Reason codes and nested responses reach the model unchanged.
  • Status lookup is a reasonable candidate for conversion because it is read-only and simple.
Recommendation

Build the curated Spring AI MCP server for the POC. Plan Kong as Gateway A in passthrough mode for production: it adds authentication, per-tool access control, rate limits and metrics without changing the server. Consider Kong conversion later for simple read-only tools on other products.

Design rules that keep the POC Kong-ready

  • Use Streamable HTTP on a single /mcp path. Every gateway can proxy that.
  • Do not put caller authentication inside the server for the POC. Leave it to the gateway, and read the caller identity from a header the gateway sets.
  • Keep backend URLs and credentials in configuration behind the PrequalClient adapter, so moving the APIs from Apigee to Kong is a config change.
  • Keep the OpenAPI specs accurate. Kong's conversion mode and your adapter both depend on them.

11Scale to all apply products

  • One server, product-prefixed tools to start (prequal_*, apply_*, paylater_*). Split into separate servers only when ownership or deployment cadence differs.
  • Keep the catalogue small. Every tool description sits in the model's context, and too many similar tools reduce accuracy. Expose business tasks, not every endpoint.
  • Make the pattern a template: adapter interface, mapper, tool class, description review, conversation tests. The second product should take a fraction of the first.
  • Version deliberately. Changing a tool's name or schema breaks agents that rely on it. Add new tools or optional fields; deprecate old ones with notice.
  • Observe agent traffic separately in Apigee and New Relic: calls per tool, error rate per tool, accept-without-offers attempts, duplicate key conflicts.

12Questions to settle with leadership

"Anyone can reach them" can mean very different systems. These answers change the design.

  1. Who is "anyone"?Internal employees using an AI assistant, internal agent platforms, or external partners. This sets the authentication model and the review path.
  2. Whose behalf does an agent act on?An agent assisting a Synchrony agent in a call centre is different from an agent acting directly for a consumer. Consent, disclosure, and audit rules differ.
  3. Which AI hosts and models are approved for applicant PII?This decides whether real data can ever flow through a given client.
  4. What disclosures must be shown before the soft inquiry and before acceptance?Compliance may require exact text; that becomes an MCP resource.
  5. Where will the server run?A new PCF app behind Apigee, or a central agent gateway if Synchrony has one planned.

13Glossary

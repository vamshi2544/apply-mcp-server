Apply MCP Server Handbook

What this repository contains, why each piece exists, and how a request travels from an AI agent to the prequal APIs and back. Read this before changing the code or connecting it to a real backend.

Spring Boot 3.5Spring AI 1.1 MCPJava 17Streamable HTTP /mcp30 tests

01Overview

This is an MCP server: a Spring Boot application that lets AI agents (GitHub Copilot, Claude, internal agent platforms) use the Apply prequalification capability by calling tools instead of REST endpoints.

It publishes three tools that map to the three business steps:

ToolBusiness stepBackend API it callsNature
prequal_get_offersCheck prequalification, get offersPOST /v1/prequal/offersSoft inquiry, needs consent
prequal_accept_offerAccept one offer, create applicationPOST /v1/prequal/offers/{offerId}/acceptIrreversible, needs confirmation and idempotency key
prequal_get_application_statusCheck application statusGET /v1/applications/{applicationId}/statusRead only

The core idea: the backend APIs are not changed. This server is a thin translation layer. It turns developer-oriented APIs (internal codes, headers, nested payloads) into agent-oriented tools (plain names, clear descriptions, flat inputs, plain-language results with a next step).

The backend paths and payloads in this repository are an illustrative contract, and by default the server uses an in-memory mock. Switching to the real APIs is configuration plus aligning one adapter class. See sections 08 and 09.

02Architecture

Three layers. Spring AI owns the protocol; we own the tools and the adapter.

What each layer is responsible for

LayerOwnsKnows nothing about
Protocol (Spring AI)The /mcp HTTP endpoint, JSON-RPC parsing, session ids, the initialize handshake, building tools/list from annotations, generating JSON schemas from method parameters, invoking the method, converting the return value and exceptions into MCP results.Prequal, Synchrony, credit cards.
Tool layer (prequal/tool)Tool names and descriptions, input validation, safety rules (consent, confirmation, key format), translating backend responses into agent-friendly results, correlation ids, logging.HTTP, headers, gateways, which backend is active.
Adapter layer (prequal/backend)The backend contract (PrequalApi), talking to the APIs (or pretending to), gateway headers, credentials, timeouts.MCP, AI agents, tool descriptions.

04End-to-end flow

One complete conversation, from connecting to an approved application. Solid arrows are calls; dashed arrows are responses.

Points to notice

  • The model never sees the backend. It sees only the tool descriptions from tools/list and the results our mapper returns.
  • Consent and choice come from the person, not the model. The descriptions tell the model to ask; the code rejects the call if consentSoftInquiry or applicantConfirmed is not true.
  • Copilot asks you to approve tool calls. Because prequal_accept_offer is marked destructiveHint: true, hosts treat it as needing explicit approval.
  • Every result has a nextStep. This is how the server steers the model through offers → accept → status without the model knowing the business process in advance.

05Messages on the wire

These are real messages captured from this server running against the mock (shortened where marked).

1. initialize

COPILOT → POST /mcp
{ "jsonrpc":"2.0", "id":1, "method":"initialize",
  "params":{ "protocolVersion":"2025-06-18", "capabilities":{}, "clientInfo":{ "name":"copilot", "version":"…" } } }
SERVER → response (+ header Mcp-Session-Id: 2ec3a669-…)
{ "jsonrpc":"2.0", "id":1, "result":{
  "protocolVersion":"2025-06-18",
  "capabilities":{ "tools":{ "listChanged":true }, … },
  "serverInfo":{ "name":"apply-mcp-server", "version":"0.1.0" },
  "instructions":"Tools for credit card prequalification. The flow is: prequal_get_offers … " } }

The session id comes back as an HTTP header. The client sends it on every later request so the server knows which conversation it belongs to. The instructions come from application.yml and give the model the overall flow up front.

2. tools/list (one of three tools shown)

SERVER → response
{ "name":"prequal_accept_offer",
  "title":"Accept a prequalified credit card offer",
  "description":"Accept one prequalified credit card offer and create a credit card application. This cannot be undone. …",
  "inputSchema":{ "type":"object",
    "properties":{
      "prequalId":{ "type":"string", "description":"The prequalId returned by prequal_get_offers." },
      "offerId":{ … }, "idempotencyKey":{ … },
      "applicantConfirmed":{ "type":"boolean", … } },
    "required":["prequalId","offerId","idempotencyKey","applicantConfirmed"] },
  "annotations":{ "readOnlyHint":false, "destructiveHint":true, "idempotentHint":true, "openWorldHint":false } }

Everything in this message is generated from the @McpTool and @McpToolParam annotations in PrequalTools.java. You never write JSON schema by hand.

3. tools/call and a successful result

COPILOT → POST /mcp
{ "jsonrpc":"2.0", "id":3, "method":"tools/call",
  "params":{ "name":"prequal_get_offers",
    "arguments":{ "firstName":"Jane", "lastName":"Doe", "dateOfBirth":"1990-04-12", "ssnLast4":"6789",
      "addressLine1":"100 Main St", "city":"Dayton", "state":"OH", "zipCode":"45402",
      "annualIncome":85000, "consentSoftInquiry":true } } }
SERVER → response (event-stream framing removed)
{ "jsonrpc":"2.0", "id":3, "result":{
  "content":[{ "type":"text", "text":"{\"decision\":\"QUALIFIED\",\"prequalId\":\"PQ-1001\",
     \"offers\":[{\"offerId\":\"OF-1001-1\",\"productName\":\"Cashback Card\",\"creditLimit\":3000,\"purchaseApr\":27.99,…},…],
     \"reason\":\"The applicant prequalified for 2 offer(s). This is not a final credit decision.\",
     \"nextStep\":\"Present each offer's product name, credit limit and purchase APR … then call prequal_accept_offer …\"}" }],
  "isError":false } }

Note what is not in the result: no SSN, DOB, income or address, and no internal code A1.

4. A rule violation

SERVER → response to accept with applicantConfirmed=false
{ "jsonrpc":"2.0", "id":4, "result":{
  "content":[{ "type":"text", "text":"The applicant has not confirmed this offer. Show them the offer's product name, credit limit
     and purchase APR, ask them to confirm they want it, and call again only after they confirm." }],
  "isError":true } }

This is a normal result with isError: true, not a protocol error. The model reads the text and acts on it. That is why every ToolCallException message is written as an instruction.

06Inside one tool call

What happens between the HTTP request arriving and the response leaving, for prequal_accept_offer.

Spring AI
Receive and route
POST /mcp arrives. Spring AI parses JSON-RPC, checks the session, finds the tool named prequal_accept_offer, converts the JSON arguments to Java parameters.
PrequalTools.traced
Correlation id and timing
Creates a UUID correlation id, puts it in the logging context (MDC), starts a timer.
PrequalTools.acceptOffer
Enforce rules
Rejects if applicantConfirmed is not true, if ids are blank, or if the idempotency key is not a UUID. Rejection = ToolCallException with an instruction for the model.
PrequalTools
Build the backend request
Creates PrequalApi.AcceptRequest in the backend's own format and calls backend.acceptOffer(offerId, request, key, correlationId).
Mock or Http backend
Call the API (or simulate it)
Http: POST to the gateway with Idempotency-Key, X-Correlation-Id, client id and API key headers. Returns BackendResponse with status and body or error code. Never throws for HTTP errors and never retries.
PrequalMapper.toAcceptResult
Translate
201 → ACCEPTED, 200 → ALREADY_ACCEPTED, 202 → IN_PROGRESS, 409/410/404/5xx → specific instruction. Status code A → APPROVED. Adds nextStep.
PrequalTools.traced
Log one line
tool=prequal_accept_offer outcome=ok correlationId=… durationMs=12. Never the arguments.
Spring AI
Respond
Serialises the AcceptResult record to JSON text inside content, or turns the exception into isError: true, and sends it back on the stream.

07What happens at startup

  1. Spring Boot reads application.yml, then application-real.yml if the real profile is active, then ./config/application-real.yml if it exists, then environment variables and command-line arguments. Later sources win.
  2. The value of prequal.backend is now fixed. Spring creates exactly one PrequalBackend bean: MockPrequalBackend has @ConditionalOnProperty(havingValue="mock", matchIfMissing=true); HttpPrequalBackend has @ConditionalOnProperty(havingValue="http").
  3. If http was chosen but the base URL, client id or API key is missing, the constructor throws and the app refuses to start with a message naming the missing setting.
  4. The chosen backend logs one line: Prequal backend: MOCK … or Prequal backend: REAL APIs via https://….
  5. Spring creates PrequalTools and injects the backend. Spring AI's annotation scanner finds the three @McpTool methods and registers them.
  6. Spring AI publishes the Streamable HTTP endpoint at /mcp. The server is ready for initialize.

08Mock or real API: where the switch lives

With a REST API you might switch behaviour per request with a header. Here the caller is an AI model, so the switch must not be something a caller can send. It is server configuration, decided once when the server starts, like a database URL.

How you control it day to day

WhereMockReal API
IntelliJRun Apply MCP (mock)Run Apply MCP (real API)
Terminal./mvnw spring-boot:runSPRING_PROFILES_ACTIVE=real ./mvnw spring-boot:run
Built jarjava -jar app.jarjava -jar app.jar --spring.profiles.active=real
PCF (later)Local and test spaces onlycf set-env apply-mcp SPRING_PROFILES_ACTIVE real in the manifest

How to check which one is running

  • Startup log: Prequal backend: MOCK (in-memory, no real APIs are called) or Prequal backend: REAL APIs via ….
  • Browser: http://localhost:8080/actuator/info returns {"prequal":{"backend":"mock"}} or "http".

Why not a per-call flag? If the switch were a tool argument, the model could choose mock or real on its own, data from two worlds could mix in one conversation, and a production server could be told to use fake data. Keeping it in configuration means whoever deploys the server decides, and the agent cannot change it.

Production guard (later): when this is deployed, the production manifest should set the real profile and the mock should not be selectable there. A simple way is to fail startup if prequal.backend=mock while a prod profile is active.

09Pointing at the real API

The tool layer does not change. Only the adapter layer and configuration do. Expect this to take hours, not days, once you have the real request and response samples.

  1. Align the contract. In PrequalApi.java, rename record fields to match the real JSON, or add @JsonProperty("realName"). Add fields the API requires (for example channel or product codes).
  2. Align paths and headers. In HttpPrequalBackend.java, set the real URIs and header names (client id, API key, correlation id, idempotency key).
  3. Align authentication. If the gateway uses an OAuth 2.0 client-credentials token instead of an API key, add token retrieval in HttpPrequalBackend (Spring Security OAuth2 client can do this). Nothing else changes.
  4. Align error parsing. parseErrorCode expects {"code": "...", "message": "..."}. Adjust to the real error body.
  5. Align code tables. In PrequalMapper.java, put the real decision codes, status codes and error codes into the switch statements.
  6. Update the HTTP test in HttpPrequalBackendTest with real (masked) sample responses, and run ./mvnw test.
  7. Add credentials locally: copy config/application-real.yml.example to config/application-real.yml and fill in lower-environment values.
  8. Run Apply MCP (real API), confirm the startup log and /actuator/info, then call the tools from MCP Inspector before trying Copilot.

Data: use lower-environment test profiles only, and do not send real applicant data through Copilot or any AI host until InfoSec approves that host.

12Tests and how to verify by hand

Run everything with ./mvnw test. Thirty tests, about 15 seconds. The test pyramid here:

  • Unit: mock rules, mapper tables, tool validation (MockPrequalBackendTest, PrequalToolsTest).
  • Adapter: real HTTP client against a local stub server (HttpPrequalBackendTest).
  • Wiring: the switch picks the right backend (BackendSelectionTest).
  • Protocol: full server, real MCP client, full flow (McpEndpointIntegrationTest).

13Run it on your Mac, then on the work laptop

Personal Mac

  1. Install a JDK 17 or later: brew install openjdk@17, or let IntelliJ download one (Project Structure → SDK → Download JDK).
  2. Install Node.js if you want MCP Inspector: brew install node.
  3. Clone: git clone https://github.com/vamshi2544/apply-mcp-server.
  4. Open the folder in IntelliJ. It imports the Maven project and shows the two run configurations from .run/.
  5. Run ./mvnw test once in the terminal. All tests should pass.
  6. Run Apply MCP (mock). Check http://localhost:8080/actuator/health shows UP.
  7. Connect MCP Inspector, then Copilot.

Work laptop: what will be different

  • Maven repository. The build downloads from Maven Central. On a corporate network it usually goes through an internal mirror (configured in ~/.m2/settings.xml). That mirror must serve org.springframework.ai 1.1.x, io.modelcontextprotocol.sdk and org.springaicommunity:mcp-annotations. Check this first.
  • Proxy and certificates. If downloads fail with SSL errors, the corporate root certificate must be in the JDK trust store. Your platform team usually has a standard fix.
  • Copilot policy. The organisation must enable "MCP servers in Copilot" for Business or Enterprise users.
  • Where the code lives. Recreate the project in the company's repository rather than pulling from a personal GitHub account, and add real contract details only there.
  • Java version. The project targets Java 17. If the company standard is 21, change java.version in pom.xml.

14Design decisions and why

DecisionWhy
Spring AI MCP server (Java), not PythonMatches the team's Spring Boot, PCF and Apigee stack, so it can be owned and deployed like any other service.
Streamable HTTP, not stdioLeadership wants a shared service. HTTP works locally and deploys behind a gateway unchanged. stdio only works on one machine.
Curated tools, not auto-generated from OpenAPIConsent, confirmation and idempotency rules are logic; a generator cannot enforce them. Descriptions written for a model outperform developer-oriented API docs.
Backend APIs unchangedWeb, mobile and partner channels depend on them. Translation happens in the tool layer.
@McpTool instead of plain @Tool@McpTool supports MCP tool annotations (read-only, destructive, idempotent hints) that hosts use to decide when to ask the user for approval.
Flat camelCase parametersA flat schema is easiest for a model to fill correctly. camelCase matches Java naming; the tool names stay snake_case.
Exceptions become isError results with instructionsThe model can recover (ask for missing consent, fix a field) instead of the conversation failing.
nextStep in every resultGuides the model through the business process without hard-coding it in the host.
Deterministic mock with trigger valuesEvery path, including rare ones (202, 409, 410), can be demonstrated and tested on demand.
Backend switch in configurationThe deployer decides; the agent cannot. Fail-fast at startup prevents half-configured real mode.
No retries in the HTTP adapterAutomatic retry of a state-changing call can create duplicate applications. Retry decisions belong to the caller with the same idempotency key.
No caller authentication in the server yetFor the POC it runs on localhost. In production the gateway (Apigee or Kong) will authenticate callers in front of /mcp.

15Adding the next apply product

  1. Create <product>/backend: contract records, backend interface, deterministic mock, HTTP implementation, properties.
  2. Create <product>/tool: @McpTool class with names like <product>_<action>, mapper, result records.
  3. Give the product its own switch, for example paylater.backend=mock|http, following the same pattern.
  4. Copy the four test classes and adapt them.
  5. Update the README tool table and mock scenarios. Spring AI picks up the new tools automatically.

Keep the total number of tools small. Every description is loaded into the model's context, and many similar tools reduce accuracy.

16Glossary

MCP
Model Context Protocol. Standard way for AI applications to discover and call tools.
Host
The AI application with the model, here GitHub Copilot in IntelliJ.
Tool
A named action with a description and JSON input schema that a model can call.
JSON-RPC 2.0
Message format of MCP: requests with id and method, responses with result or error.
Streamable HTTP
MCP transport over a single HTTP endpoint; responses can stream as server-sent events.
Mcp-Session-Id
Header identifying one client connection across requests.
Tool annotations
Hints like readOnlyHint and destructiveHint that tell hosts how risky a tool is.
isError
Flag on a tool result meaning the call failed in a way the model should read and act on.
Spring profile
A named set of configuration (here real) activated at startup.
MDC
Mapped Diagnostic Context: per-thread logging fields, used for the correlation id.
Idempotency key
A unique id for one intended action, so retries cannot repeat it.

Apply MCP Library

Four documents that explain, from first principles, how to expose Apply products such as credit card prequalification to AI agents through the Model Context Protocol: what MCP is, how agents are authenticated, how it fits on Apigee and PCF, and how to get from our proof of concept to production.

01Your questions, answered briefly

  1. Can we authenticate an agent before it lands on Apigee or Kong?

    Yes. Before calling us, the AI application obtains an OAuth access token from our corporate identity provider: an employee signs in with SSO and MFA, or an agent platform authenticates with a certificate. Apigee is the first component on our side; it validates the token (signature, issuer, audience, scopes for the specific tool) and rejects everything else. The MCP server validates again. Network rules can block unknown sources even earlier. Document 2

  2. Why use Apigee at all instead of exposing the PCF app directly?

    A PCF route only delivers traffic. Apigee decides who may call, how often and with which permissions, gives analytics and threat protection, and is the pattern security has already approved for our APIs. An MCP server reachable directly would bypass all of it. Document 3

  3. Why Spring Boot? Is it only because we have PCF?

    Mostly yes, and that is a good reason. MCP is language-neutral. Spring Boot reuses our skills, pipeline, PCF buildpacks, Spring Security, Splunk and New Relic setup, and support model. Python or Node would work equally well technically but would be a new runtime to operate. Document 3

  4. What is the enterprise standard for MCP?

    The standard is the protocol (governed by the Agentic AI Foundation under the Linux Foundation) and its OAuth 2.1 authorization profile. The common enterprise pattern: remote servers over Streamable HTTP, owned by the domain team, behind the existing API gateway, authenticated with the corporate identity provider, with curated tools for important actions, catalogued and monitored. Document 3

  5. We have APIs. What comes next?

    Decide who agents act for and which AI hosts are approved; make API specs agent-ready; connect the MCP server to real APIs in a lower environment; add OAuth at Apigee and in the server; deploy on PCF behind an Apigee MCP proxy; pilot with real users; harden and launch; repeat for other products. 04Recommended decisions at a glance

TopicRecommendation
APIsUnchanged. Enrich their Swagger specs to agent-ready.
ToolsCurated Spring Boot MCP server for state-changing and regulated actions; generated read tools later (Apigee MCP preview).
TransportStreamable HTTP, stateless mode, one /mcp endpoint.
Front doorApigee north proxy; MCP PCF route internal only.
AuthenticationOAuth 2.1 with the corporate IdP: SSO + PKCE for employees, client credentials + mTLS for agent platforms.
AuthorizationPer-tool scopes enforced at Apigee (Mcp-Name) and in code; ownership checks on ids.
DownstreamThrough Apigee with token exchange; service credentials until available. Never token passthrough.
Human controlConsent and confirmation enforced in code; MRTR confirmation when supported.
OperationsSplunk audit index, New Relic tracing, per-tool dashboards and alerts.

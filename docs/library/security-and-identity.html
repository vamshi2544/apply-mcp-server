Agent security and identity

How to know who is calling our MCP server, what they are allowed to do, and how that identity travels safely from the AI assistant, through Apigee, to the MCP server and on to the prequal APIs. Written for someone who knows API keys and Apigee but has not worked with OAuth for agents.

Reading time ~45 minMCP authorization 2026-07-28OAuth 2.1

01The short answer

Can we authenticate an agent before it reaches our gateway?

Yes, and the MCP standard defines how. The agent logs in with our corporate identity provider before it ever calls us and receives an access token. Apigee checks that token on every request before anything reaches PCF. The MCP server checks it again, then uses its own credentials to call the APIs.

Put precisely, there are three moments:

  1. Before the request: the AI assistant obtains a token from the identity provider. An employee signs in with normal corporate single sign-on and MFA. An agent platform authenticates as a service with a certificate or signed key. No token, no access.
  2. At the front door: Apigee is the first thing on our side that the request touches. It rejects anything without a valid token for this MCP server, checks the scopes for the tool being called, and applies quotas. Network rules can also stop unknown networks from reaching Apigee at all.
  3. Behind the door: the MCP server validates the token again (defence in depth), applies business rules, and calls the prequal APIs with a separate token addressed to them. The client's token is never forwarded.

Key idea: the gateway does not log the agent in; the identity provider does. The gateway is where we check the result of that login, which is the earliest point we control.

02Who has to be identified

In a normal REST integration you usually identify one thing: the calling application (an Apigee API key or client id). In an agent integration there are up to five identities, and mixing them up is the source of most security mistakes.

IdentityQuestion it answersHow it is provenWho checks it
1. Person (employee)Which human asked for this?Corporate SSO and MFA at the identity provider; appears as sub in the tokenApigee and MCP server
2. AI application (the agent or host)Which software is calling? Copilot, Claude, the call-centre assistant?OAuth client id; for services a certificate (mTLS) or signed JWTIdentity provider at token issue; Apigee per call
3. MCP serverIs this really our server calling the API?Its own client credentials or workload identityIdentity provider and Apigee (internal proxy)
4. Backend APIIs this the real prequal API?TLS certificate, internal routingMCP server
5. Identity providerIs this token genuine?Token signature against the IdP's published keys (JWKS)Everyone who validates tokens

The applicant is not the caller. In the first use cases (an employee or internal agent assisting an applicant), the applicant's name, date of birth and SSN digits are data in the request, not a login. We authenticate the employee and the application. Consent is recorded as a business fact. If agents later act directly for consumers, consumer identity (customer login, OTP, device trust) becomes a separate, larger design, closer to our existing digital channels.

03Authentication, authorization, consent: three different things

TermQuestionPrequal exampleMechanism
Authentication (authN)Who are you?Employee E12345 using the Copilot applicationSSO login, token signature
Authorization (authZ)What may you do?May check prequal; may not accept offers unless in the call-centre groupScopes, groups, Apigee API products, per-tool rules, server checks
Consent and confirmationDid the applicant agree to this specific action?Applicant agreed to a soft inquiry; applicant confirmed the Cashback CardBusiness rules in the MCP server; host approval prompt; MRTR confirmation; audit record

OAuth handles the first two. The third is our business logic, and it must be enforced in the MCP server regardless of how good the token is. A perfectly authenticated employee can still be talked into the wrong action by a misled model.

04Defence in depth: the layers

Each layer stops a different failure. Layers 1 to 4 act before or as the request arrives at Apigee.

1
Network
Only corporate networks, approved agent platforms, or private connectivity can reach the MCP endpoint at all. IP allowlists, WAF, DDoS protection at the edge. Unknown traffic never reaches Apigee's MCP proxy.
2
Transport
TLS everywhere. Mutual TLS (client certificates) for service-to-service callers such as internal agent platforms.
3
Client identity
Only registered AI applications get tokens. The identity provider knows each client id; Apigee knows each as a developer app tied to an API product.
4
User identity
The employee signs in through corporate SSO with MFA. The token carries who they are and their groups.
5
Token check at Apigee
Signature, issuer, audience (must be this MCP server), expiry, scopes. Invalid means HTTP 401 with discovery information. Quotas and spike arrest per client.
6
Per-tool authorization
Apigee reads Mcp-Name and allows the tool only if the token has the scope or group for it. Wrong scope means HTTP 403 insufficient_scope.
7
MCP server checks
Re-validates the token (never trust the network alone), checks business authorization (is this prequalId owned by this caller?), and enforces consent and confirmation rules.
8
Human in the loop
Host approval prompts for destructive tools; MRTR confirmation of the exact offer before acceptance.
9
Downstream credentials
The MCP server calls the APIs with its own credentials or an exchanged token addressed to the API. Never with the client's token.
10
Audit and monitoring
Who (person and application), what tool, which ids, outcome, correlation id, across Apigee, MCP server and APIs. No PII in logs. Alerts on unusual patterns.

05OAuth in ten minutes, for API people

You already use OAuth if your Apigee proxies issue or verify tokens. MCP uses OAuth 2.1, which is OAuth 2.0 with the risky options removed (no implicit flow, no password grant, PKCE mandatory).

OAuth roleIn our setup
Resource ownerThe employee (or, for machine flows, the agent platform itself)
ClientThe AI application: Copilot, Claude, an internal agent
Authorization serverThe corporate identity provider
Resource serverThe MCP server, with Apigee as its front door

What is inside an access token

DECODED JWT ACCESS TOKEN (ILLUSTRATIVE)
{
  "iss": "https://login.corp.example.com",          // who issued it: must be our IdP
  "aud": "https://mcp.apply.example.com/mcp",       // who it is for: must be THIS MCP server
  "sub": "E12345",                                  // the employee
  "client_id": "copilot-jetbrains",                   // the AI application
  "scope": "prequal.check application.read",       // what it may do
  "groups": ["apply-callcentre"],
  "iat": 1791830000, "exp": 1791830900               // short life: 15 minutes
}

The token is signed by the identity provider. Anyone can verify the signature with the provider's public keys (published at a JWKS URL), so Apigee and the MCP server can validate it without calling the identity provider on each request.

The grant types that matter

GrantWho uses itHow it worksOur use
Authorization code + PKCEApps acting for a personBrowser opens the IdP login page; the person signs in; the app receives a one-time code and swaps it for a token, proving with PKCE that it started the flowEmployees using Copilot or Claude
Client credentialsServices acting for themselvesThe service proves its identity (certificate or signed JWT) and receives a token directlyInternal agent platforms; the MCP server calling APIs
Token exchange (RFC 8693)A service acting on behalf of the original callerSwap token A for token B with a different audience, keeping the original person in the tokenMCP server calling prequal APIs with user context
JWT bearer / ID-JAGEnterprise-managed accessAn identity assertion from the corporate IdP is exchanged for an access tokenEnterprise-managed authorization (section 10)
Refresh tokenLong conversationsObtain a new access token without signing in againHandled by the host

Scopes name permissions (prequal.check). Audience names the intended recipient. A token with the right scope but the wrong audience must be rejected; that single check prevents most token-reuse attacks.

06What the MCP specification requires

Authorization is optional in MCP, but for any HTTP server handling customer data we must implement it, and when we do, the specification is precise. The key requirements in 2026-07-28:

RequirementApplies toWhat it means for us
The MCP server is an OAuth 2.1 resource serverServerIt accepts bearer tokens and validates them; it does not have to issue them.
Publish OAuth Protected Resource Metadata (RFC 9728)Server MUSTA JSON document at /.well-known/oauth-protected-resource telling clients which identity provider to use and which scopes exist.
Answer 401 with WWW-Authenticate: Bearer resource_metadata="…"ServerHow a client discovers where to log in. Can be done by Apigee.
Resource indicators (RFC 8707)Client MUST send; server MUST validate audienceTokens are minted for exactly our MCP URL and are useless elsewhere.
Tokens only in the Authorization header, on every requestClientNever in the URL or query string.
No token passthroughServer MUST NOTWe never forward the client's token to the prequal APIs.
Client registration: Client ID Metadata Documents, pre-registration, or (deprecated) Dynamic Client RegistrationClient and IdPEnterprise practice: pre-register each approved AI application with the IdP.
Issuer validation (RFC 9207)ClientProtects clients against identity-provider mix-up attacks.
Scope challenges: 403 insufficient_scope with required scopesServer SHOULDWhen a token lacks prequal.accept, tell the client so it can ask for more (step-up).
Least-privilege scopesServer and clientSmall baseline scope; elevated scopes only for risky tools.

Example: our protected resource metadata

GET https://mcp.apply.example.com/.well-known/oauth-protected-resource
{
  "resource": "https://mcp.apply.example.com/mcp",
  "authorization_servers": ["https://login.corp.example.com"],
  "scopes_supported": ["prequal.check", "application.read"],
  "bearer_methods_supported": ["header"],
  "resource_name": "Apply prequalification tools"
}

prequal.accept is deliberately not in scopes_supported. It is requested only when a client tries to accept an offer and receives a scope challenge, so ordinary sessions never carry it.

07Flow A: an employee using an AI assistant

This is the main scenario: a call-centre or operations employee uses Copilot or Claude, and the assistant calls our tools on their behalf.

What each party does

  • Client (AI assistant): discovers the identity provider from our metadata, runs authorization code + PKCE with resource set to our MCP URL, stores and refreshes the token, sends it on every call.
  • Identity provider: signs the employee in with SSO and MFA, applies policy (is this person allowed to use this AI application with this resource?), issues a short-lived token with audience, scopes and groups.
  • Apigee: serves the 401 challenge and metadata, verifies the token, maps the client id to a developer app and API product, applies per-tool policy and quotas, forwards to PCF.
  • MCP server: verifies the token again, reads the employee and application identity, applies business authorization, writes the audit record.

What the employee experiences: the first time they use the prequal tools, a browser window shows the corporate login (often skipped silently if already signed in). After that, nothing until the token expires and the assistant refreshes it.

08Flow B: an internal agent platform (no person signing in)

An internal service, for example a call-centre assistant that runs on its own servers, calls our tools as itself.

  • The platform is registered with the identity provider as a confidential client and proves its identity with private_key_jwt (a JWT signed with its private key) or a client certificate, not a shared secret.
  • Apigee additionally requires mutual TLS from this platform's network.
  • The client-credentials pattern for MCP is described in a draft MCP authorization extension. Enterprises can use it today because both ends are under our control.
  • If the platform acts for a specific employee, it should pass that employee's identity in a token (token exchange or an on-behalf-of token from the IdP), not as a plain header the platform could forge.

09From the MCP server to the prequal APIs

The MCP server receives token A, addressed to itself. It now needs to call the prequal APIs, which are protected by Apigee as today. There are three options, and one of them is forbidden.

OptionHowVerdict
Token passthroughForward token A to the prequal APIForbidden by the MCP specification. Token A is addressed to the MCP server; reusing it breaks audience checks and creates confused-deputy risk.
Service credentials + asserted userMCP server calls Apigee with its own client credentials (as any consumer app does today) and sends the employee id in a header for auditSimplest; good for the first release. The API trusts the MCP server to tell the truth about the user.
Token exchange (RFC 8693)MCP server swaps token A for token B addressed to the prequal API, still naming the employee, with the MCP server recorded as the actorBest. Every hop sees a token addressed to it; the employee is cryptographically carried end to end.

10Enterprise-managed authorization (EMA)

With standard MCP authorization, every employee has to authorize every MCP server separately, and security teams have no single place to see or control who can use which server. Enterprise-Managed Authorization is an official MCP extension, marked stable in June 2026, that moves this decision into the corporate identity provider.

  • The employee signs in to the AI application with corporate SSO.
  • The application asks the identity provider for an Identity Assertion JWT Authorization Grant (ID-JAG) for our MCP server. The identity provider applies policy: group, role, conditional access.
  • The application exchanges the ID-JAG with the MCP server's authorization server for an access token.
  • Admins enable the server once; employees in the right groups get access automatically; there is one audit trail.

Status to check: at the time of writing, Okta (through its Cross App Access feature) was the first supported identity provider, and Anthropic's Claude products and a preview of Visual Studio Code were named as supporting clients. Ask the identity team whether our provider supports ID-JAG. If not, standard OAuth (flow A) works with any OAuth 2.1 compliant provider and is the starting point.

In Apigee

An MCP proxy is an ordinary Apigee proxy whose target is the MCP server's PCF route. Typical policies, in order:

  1. Return the protected resource metadata for GET /.well-known/oauth-protected-resource.
  2. If no bearer token: raise 401 with the WWW-Authenticate header pointing at the metadata.
  3. Verify the JWT against the identity provider's JWKS (VerifyJWT policy): issuer, audience, expiry.
  4. Identify the client application and its API product; apply Quota and SpikeArrest.
  5. Read Mcp-Name; compare with the scopes or groups in the token; raise 403 insufficient_scope when missing.
  6. Forward to the MCP server (keeping the token for the server's own validation), with a correlation id.

If we use Apigee's own MCP feature (in preview) for generated tools, the same API-product controls apply to it.

In the MCP server (Spring Boot)

Spring Security's OAuth2 resource server validates JWTs with a few lines of configuration (issuer-uri or jwk-set-uri, plus an audience check). The community module spring-ai-community/mcp-security adds MCP-specific helpers (protected resource metadata, audience validation) for Spring AI servers. It is labelled work in progress, so evaluate it or use plain Spring Security. Method security (@PreAuthorize("hasAuthority('SCOPE_prequal.accept')")) on each tool method gives per-tool authorization in code.

application.yml (MCP server, illustrative)
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.corp.example.com          # our IdP
          audiences: https://mcp.apply.example.com/mcp      # reject tokens for anything else

12Scope and permission design for Apply tools

ScopeToolsWho gets itNotes
prequal.checkprequal_get_offersApproved employee groups and agent appsCreates a soft inquiry; not read-only.
application.readprequal_get_application_statusSame as aboveRead only. Server checks the caller may see this application.
prequal.acceptprequal_accept_offerNarrower group; requested by step-upIrreversible. Requires confirmation; audit every call.
  • Name scopes by business capability, not by tool, so they survive tool changes and apply to other products.
  • Map scopes to identity-provider groups that already exist for the call centre or operations, where possible.
  • Never issue a wildcard scope (apply.*, all).
  • Bind state to the caller: store which employee and application created each prequalId; reject accept or status calls on ids the caller does not own. The specification warns explicitly against treating possession of an id as authorization.

14Audit and monitoring

For every tool call, record one structured audit event (separate from debug logs):

AUDIT EVENT (ILLUSTRATIVE)
{ "ts": "2026-10-12T20:15:03Z", "correlationId": "7f3c…",
  "user": "E12345", "client": "copilot-jetbrains", "tool": "prequal_accept_offer",
  "prequalId": "PQ-1001", "offerId": "OF-1001-1", "idempotencyKey": "7c9e…",
  "confirmation": "mrtr", "outcome": "ACCEPTED", "applicationId": "APP-55001", "durationMs": 412 }
  • No applicant PII in the audit event; the ids link to records in the systems of record.
  • Propagate the correlation id and trace context from Apigee through the MCP server to the APIs (the 2026-07-28 specification documents OpenTelemetry traceparent in _meta).
  • Dashboards per tool: call rate, error rate, latency, rejections by reason (no consent, no confirmation, insufficient scope, ownership).
  • Alerts: spikes in accept calls, repeated 403s from one client, unusual hours, many prequals from one employee.

15Security review checklist

  • Only remote Streamable HTTP; no stdio in production
  • MCP endpoint reachable only through Apigee
  • Protected resource metadata published at the public URL
  • 401 with WWW-Authenticate on missing or bad token
  • JWT signature, issuer, audience, expiry checked at Apigee
  • Same checks repeated in the MCP server
  • Per-tool scopes enforced at Apigee and in code
  • Approved AI clients pre-registered; others rejected
  • mTLS for service-to-service clients
  • No token passthrough; exchange or service credentials downstream
  • Ids bound to the caller and checked on every call
  • Consent and confirmation enforced in code
  • Idempotency on all state-changing calls
  • No PII in results or logs
  • Audit event per call, retained per policy
  • Quotas, spike arrest, timeouts configured
  • Descriptions reviewed and covered by tests
  • AI hosts approved by InfoSec for the data classification

16Questions to take to the identity and security teams

  1. Which identity provider do we use for workforce SSO, and is it OAuth 2.1 / OpenID Connect compliant?
    Needed for flow A. Most enterprise providers are.
  2. Can it issue access tokens with a custom audience (resource indicators) for the MCP server?
    Required for audience binding.
  3. Does it support token exchange (RFC 8693)?
    Decides how the MCP server calls the APIs with user context.
  4. Does it support ID-JAG / enterprise-managed authorization?
    Decides whether we can centrally manage access without per-server consent.
  5. Which AI hosts are approved, and for which data classifications?
    Copilot, Claude, internal platforms; can applicant PII flow through them?
  6. Which groups should receive prequal.check and prequal.accept?
    Business owners decide; identity team implements.
  7. Is Apigee VerifyJWT against the IdP's JWKS an approved pattern, and do we terminate mTLS at Apigee?
    Confirms the gateway design.
  8. What audit retention and format does compliance require for agent-initiated credit actions?
    Shapes the audit event.

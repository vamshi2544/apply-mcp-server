MCP reference architecture

How the Apply MCP server fits into the infrastructure we already run (Apigee, PCF, Spring Boot, Splunk, New Relic, corporate SSO), why each piece is there, and what the industry treats as the enterprise pattern for MCP.

Reading time ~40 minApigee · PCF · Spring Boot

01Short answers

Why Apigee and not the PCF route directly?

A PCF route only delivers traffic. Apigee is where we decide who may call, how often, and with what credentials, and where we see and audit the traffic. An MCP server reachable directly on its PCF route would bypass every control we apply to our APIs today. The rule stays the same as for APIs: nothing customer-facing or agent-facing is reachable except through the gateway.

Why Spring Boot?

Not because MCP requires Java; MCP is language-neutral. We chose Spring Boot because the team, the PCF platform, the build pipeline, the security libraries, the observability agents and the production support model already exist for it. A Python or Node service would be just as valid technically, but would be the first of its kind for the team to run in production.

What is the enterprise standard for MCP?

The standard is the protocol itself (MCP, now governed by the Agentic AI Foundation under the Linux Foundation) with its OAuth 2.1 authorization profile. There is no mandated product. The pattern enterprises have converged on is: remote MCP servers over Streamable HTTP, owned by the domain team, behind the existing API gateway, authenticated by the corporate identity provider, listed in a catalogue, and monitored like any other service.

03Why not expose the MCP server directly on PCF

A PCF route (for example apply-mcp.apps.internal…) is a hostname the PCF router forwards to our application instances. It does TLS and load balancing. It does nothing else. Compare what Apigee adds:

ConcernPCF route onlyThrough Apigee
Who may callAnyone who can reach the routeOnly registered apps with a valid token for this resource
Token validationMust be coded into every serviceCentral policy, same as all APIs; the service re-checks
Per-tool permissionsCode onlyPolicy on Mcp-Name plus code
Rate limits, spike arrestNonePer app, per tool
Analytics: who called what, how oftenApplication logs onlyStandard Apigee analytics alongside all other API traffic
Threat protection (payload size, JSON threats)NoneStandard policies
Stable public URL and versioningTied to PCF space and app namesStable proxy URL; backend can move
Consistency with security reviewNew exception to justifySame pattern InfoSec already approved
Future gateway featuresNoneApigee MCP proxy (preview), API hub catalogue

And on the way out: MCP server to the prequal APIs

The MCP server is a new consumer of the prequal APIs. Two ways to reach them:

PathProsCons
Through Apigee (as a registered app)Same as every other consumer; same analytics, quotas, credentials; API teams see agent traffic separatelyOne extra network hop (small)
Direct PCF container-to-containerLowest latencyBypasses API policies and analytics; needs network policy approval; agent traffic invisible to API owners

Recommendation: go through Apigee. It keeps agent traffic visible to the API owners and requires no new trust model.

Conclusion: the deciding factors are operational, not technical. If the organisation later standardises agent services on another runtime, the tool contracts (names, descriptions, schemas) carry over unchanged; only the implementation moves.

Version path: the proof of concept uses Spring Boot 3.5 with Spring AI 1.1. Spring AI 2.0 (June 2026) requires Spring Boot 4 and ships MCP Java SDK 2.0. Plan the production build on the Spring Boot version our platform supports, and check Java SDK support for the 2026-07-28 protocol before relying on MRTR or the new headers.

09Inside the MCP server

1
Security filter
Spring Security OAuth2 resource server: JWT validation, audience, scopes to authorities.
2
MCP protocol
Spring AI MCP server: /mcp endpoint, JSON-RPC, tool discovery from annotations, schema generation. Stateless mode.
3
Tool layer
@McpTool methods: validation, consent and confirmation rules, ownership checks, per-tool authorization, audit event.
4
Translation
Mapper: internal codes to plain results, next steps, PII trimming.
5
Adapter
Backend interface with mock and HTTP implementations; token exchange or service credentials; timeouts; no automatic retries on writes.
6
Operations
Actuator health, metrics per tool, tracing, structured logs to Splunk, New Relic agent.

Scaling and resilience

  • Stateless: use Spring AI's STATELESS protocol mode; any instance answers any request; no sticky sessions; scale with cf scale or autoscaler.
  • Ownership data (which caller created which prequalId) must not live in instance memory. Keep it in the backend, or in a shared store such as Redis or GemFire.
  • Timeouts shorter than the host's tool timeout so the model receives a clear message.
  • Circuit breaker on reads (Resilience4j); writes fail fast with "outcome unknown, retry with the same key".
  • Connection pools sized for backend capacity; quotas at Apigee protect the APIs from agent loops.

Whatever the split, keep the total number of tools an agent sees small, and allow enabling or disabling individual tools by configuration per environment.

12Observability

  • Correlation: Apigee generates or forwards a correlation id; the MCP server logs it and sends it to the APIs; New Relic distributed tracing links the spans. The 2026-07-28 specification also lets clients pass OpenTelemetry trace context in _meta.
  • Metrics per tool: calls, errors by reason, latency percentiles, rejected-by-rule counts.
  • Audit stream: one structured event per call to a dedicated Splunk index with the retention compliance requires.
  • Dashboards: agent traffic by client application, by tool, by employee group.
  • Alerts: error spikes, quota exhaustion, unusual accept volume, repeated authorization failures.

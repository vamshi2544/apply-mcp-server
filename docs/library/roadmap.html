Roadmap and build guide

We have APIs, Swagger specs in Apigee, and a working MCP proof of concept with a mock backend. This document is the path from here to a production MCP service for Apply products: phases, owners, the code changes still needed, checklists, risks, and answers to the questions that will come up.

Reading time ~35 minFrom POC to production

01Once we have APIs, what is next?

In one paragraph

Decide who the agents will act for and which data may flow to which AI applications. Make the API descriptions agent-ready. Connect the MCP server to the real APIs in a lower environment. Add OAuth at Apigee and in the server. Deploy it on PCF behind an Apigee MCP proxy. Pilot it with a small group of real users and measure. Then harden for production, launch, and repeat the pattern for the next Apply products.

03Phase 2: contracts

  • Score the prequal, accept and status Swagger specs on the L0–L4 scale (see the machine-readable APIs briefing) and lift them to L3: explain every code, document errors and idempotency, add examples.
  • Freeze the three tool contracts: names, descriptions, input schemas, outputs, error messages, retry rules.
  • Review with compliance: wording of consent requests and the explanation of decisions.
  • Write the conversation evaluation set (at least 20 scripted conversations including misuse attempts).

Exit: signed-off tool contracts, agent-ready specs, evaluation set in the repository.

04Phase 3: real backend in a lower environment

  1. Align PrequalApi records with the real request and response JSON.
  2. Set real paths, headers and error parsing in HttpPrequalBackend.
  3. Replace the illustrative code tables in PrequalMapper with the real decision, status and error codes.
  4. Register the MCP server as a developer app in Apigee for SIT; obtain client credentials; store them in a PCF service binding or vault.
  5. Run the adapter tests with masked real samples; run the protocol tests against SIT.

Exit: every decision path reproduced in SIT through the MCP tools, visible in Apigee analytics and Splunk.

05Phase 4: security

  • Apigee north proxy: protected resource metadata, 401 challenge, VerifyJWT against the IdP, per-tool scope policy on Mcp-Name, quotas.
  • MCP server: Spring Security resource server with audience validation; @PreAuthorize per tool; reject the mock in production.
  • Ownership binding: record the creating user and client for each prequalId and applicationId; check on every call.
  • Downstream: token exchange if the IdP supports it, otherwise service credentials plus asserted user id.
  • Audit events to a dedicated Splunk index.
  • Threat model walkthrough with InfoSec (document 2, section 13).

Exit: security tests pass for missing token, wrong audience, wrong scope, other user's id, missing consent, missing confirmation, duplicate acceptance.

06Phase 5: platform deployment

  • PCF space and app with an internal-only route; at least two instances; Spring AI STATELESS protocol mode.
  • Apigee north proxy pointing at the internal route; environment-specific configuration.
  • New Relic APM and distributed tracing; Splunk log and audit indexes; dashboards and alerts.
  • CI/CD pipeline identical to the API services, including dependency scanning.

08Phase 7: production readiness checklist

  • Security review approved
  • InfoSec approval of hosts and data flows
  • Compliance sign-off on consent and disclosures
  • Performance test at expected peak plus margin
  • Quotas and spike arrest tuned
  • Runbook: alerts, dashboards, common failures
  • On-call trained on MCP traffic
  • Rollback plan: disable tools by configuration
  • Kill switch: revoke client apps in Apigee or IdP
  • Audit retention configured
  • Production guard against mock backend
  • Conversation evaluation passing on the release build
  • Staged rollout plan by user group
  • Support contacts for identity and Apigee teams

09Phase 8: scale out

  • Next products: Direct Apply, multi-product prequal, PayLater, following the same package pattern (backend, tool, tests).
  • Generated read tools: Apigee MCP proxy for simple lookups once specs are agent-ready and the preview is available.
  • MRTR confirmation for accept once the Java SDK and target hosts support the 2026-07-28 protocol.
  • Enterprise-managed authorization if the identity provider supports ID-JAG.
  • Catalogue: list approved tools in Apigee API hub or an internal registry.
  • Resources: publish disclosures and product terms as MCP resources.

12Definition of done for any new tool

  • Business task named and owned
  • Underlying API spec at L3
  • Name follows product_action
  • Description: what, when, prerequisites, next step, retry rule
  • Inputs flat with schema constraints
  • Results plain, minimal, with nextStep, no PII echo
  • Annotations set correctly
  • Scope assigned; enforced at Apigee and in code
  • Rules enforced in code and tested
  • Ownership check for any id it accepts
  • Idempotency for state changes
  • Audit event emitted
  • Unit, adapter, protocol tests
  • Conversation evaluations added
  • Documentation and README updated
  • Reviewed like an API contract change

14Frequently asked questions

  1. Is MCP just a wrapper around our APIs?

    Technically yes: a thin layer. Practically it is a new contract, written for a model rather than a developer, plus the safety rules that a model needs and a developer does not.

  2. Can the agent call our APIs directly without MCP?

    Some agent frameworks can call OpenAPI endpoints directly. You then lose the curated descriptions, the business rules, the PII trimming, and the standard way every AI host connects. MCP is the standard interface for agents; the APIs stay the interface for applications.

  3. How do we authenticate the agent before it reaches the gateway?

    The agent signs in with the corporate identity provider and gets a token before it calls us; Apigee validates the token as the first step on our side. Network rules can block unknown sources earlier. Details in document 2.

  4. Why can't we use API keys like for partners?

    An API key identifies an application, not the person using it, and cannot be scoped per user or expire quickly. MCP's standard is OAuth, which every MCP host supports. API keys are acceptable only for local testing.

  5. Why Apigee in front if the MCP server already validates tokens?

    Central policy, quotas, analytics and threat protection, plus the same approved pattern as every API. The server validates as well, so a bypassed gateway is still safe.

  6. Why Spring Boot and not Python, which most MCP examples use?

    Operations: our team, pipeline, PCF buildpacks, security libraries and monitoring are Java. The protocol is language-neutral, so the choice can change later without changing the tool contracts.

  7. Does the 2026 protocol change break our design?

    No. It removes sessions, and our tools never depended on them. It adds features we want (gateway headers, MRTR). We upgrade the SDK when it supports the new version.

  8. Can Apigee replace the MCP server?

    For simple read tools, possibly (Apigee MCP preview). Not for accept or anything that needs consent, confirmation or ownership checks.

  9. What about Kong?

    If production moves to Kong, it plays the same role as Apigee: front door, token validation (AI MCP OAuth2 plugin), per-tool access control, and optionally generated tools. The MCP server does not change.

  10. How many tools can we expose?

    There is no protocol limit, but model accuracy drops as similar tools multiply. Keep each agent's view to the tools it needs; prefer task-level tools.

  11. What if the model invents an offer id?

    The backend rejects unknown ids, the mapper tells the model to use exact ids, and the ownership check stops ids from other users.

  12. What if the model retries accept with a new idempotency key?

    The backend allows one acceptance per prequalification, so the second attempt is rejected with a clear message. The description and error texts also tell the model not to do it.

  13. Where is the applicant's consent stored?

    As a business record via the prequal API (consent flag and timestamp), plus the MCP audit event. Compliance decides the exact requirements.

  14. Can customers use this directly through their own AI assistants?

    Not in this design. Consumer-direct agents need customer authentication, fraud controls and different consent handling. Treat it as a separate initiative.

  15. How do we test without an LLM?

    MCP Inspector and the protocol tests exercise the server without any model. Copilot in IntelliJ provides a model for conversation testing.

  16. Who owns the tool descriptions?

    The Apply team, with review by business and compliance, under version control like an API contract.

15Acronyms and standards

OAuth 2.1
Current consolidated version of OAuth 2.0; required by MCP authorization.
OIDC
OpenID Connect: identity layer on OAuth, used for SSO.
JWT
JSON Web Token: signed token format for access tokens.
JWKS
JSON Web Key Set: the IdP's public keys used to verify JWT signatures.
PKCE
Proof Key for Code Exchange: protects the login code from interception.
RFC 9728
OAuth Protected Resource Metadata: how our server says where to log in.
RFC 8707
Resource Indicators: tokens minted for one specific server.
RFC 8693
Token Exchange: swapping one token for another with a different audience.
RFC 9207
Issuer identification in authorization responses: prevents mix-up attacks.
CIMD
Client ID Metadata Document: a client identified by an HTTPS URL describing it.
DCR
Dynamic Client Registration: deprecated in MCP 2026-07-28.
ID-JAG
Identity Assertion JWT Authorization Grant: used by enterprise-managed authorization.
EMA
Enterprise-Managed Authorization: MCP extension for IdP-controlled access.
MRTR
Multi Round-Trip Request: server asks for input, client retries with answers.
mTLS
Mutual TLS: both sides present certificates.
PRM
Protected Resource Metadata (RFC 9728).

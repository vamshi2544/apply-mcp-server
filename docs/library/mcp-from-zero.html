MCP from zero

Everything about the Model Context Protocol you need before designing or reviewing an MCP server, explained for someone who knows REST APIs well and has never worked with AI agents. It covers the protocol as of the 2026-07-28 specification and notes where our proof of concept still uses the earlier version.

Reading time ~35 minSpec 2026-07-28No AI background assumed

01Why MCP exists

A large language model (LLM) on its own can only read text and write text. It cannot call an API, read a database, or check an application status. To do useful work it needs tools: functions that some program runs on its behalf.

Before MCP, every AI product invented its own way of plugging tools in. If you wanted your prequal API usable from Claude, from GitHub Copilot and from an internal agent platform, you wrote three different integrations, in three different formats, and maintained all three. With many AI products and many backend systems, that becomes an N × M problem.

MCP is the standard plug. You build one MCP server for prequal. Any AI application that speaks MCP can discover its tools and call them, without integration code specific to that application.

Analogy you already knowMCP is to AI agents what OpenAPI plus HTTP is to applications. OpenAPI describes what an API offers; HTTP carries the calls. In MCP, the server describes its tools in a standard format, and a standard message protocol carries the calls. The difference is the consumer: a program written by a developer versus a model deciding at run time.
REST API worldMCP world
ConsumerCode a developer wroteAn AI model choosing tools at run time
DescriptionOpenAPI spec, read at build timetools/list result, read at run time by the model
Unit of workEndpoint (POST /v1/prequal/offers)Tool (prequal_get_offers)
Message formatHTTP verbs, paths, JSON bodiesJSON-RPC 2.0 messages over HTTP POST
Who decides to callThe developer's code, deterministicallyThe model, based on the conversation and the tool descriptions
Error handlingCode handles status codesThe model reads the error text and decides what to do

02How a model actually uses a tool

This is the most important idea to get right, because it explains every design rule later. The model never calls your server. The application around the model (the host) does. The model only writes a structured request saying "call this tool with these arguments", and the host carries it out.

  1. When the conversation starts, the host fetches the tool list from each connected MCP server and puts the tool names, descriptions and input schemas into the model's context, next to the conversation.
  2. The person asks something. The model reads the conversation and the tool descriptions. If a tool fits, it replies with a structured tool call: tool name plus JSON arguments.
  3. The host (through its MCP client) sends that call to the MCP server.
  4. The MCP server runs it, for us by calling the prequal REST API.
  5. The result comes back to the host.
  6. The host appends the result to the conversation and asks the model to continue.
  7. The model either calls another tool or writes the answer.

Consequences you should remember

  • Descriptions are the interface. The model chooses tools only from names, descriptions and schemas. A vague description causes wrong calls. This is why we spend more effort on descriptions than on code.
  • Results become model input. Whatever you return is read by the model and may be shown to the person or stored by the host. Return only what is needed; never return data the person should not see.
  • The model can be wrong or misled. It can choose the wrong tool, invent an argument, or follow instructions hidden in text it read (prompt injection). Every rule that matters must be enforced in server code, not just described.
  • Context is limited. Every tool description occupies space in the model's context. Fifty similar tools make the model worse at choosing. Expose business tasks, not every endpoint.
  • The model has no memory between conversations. It knows only what the descriptions and results tell it in this conversation.

Local versus remote servers. A local server runs on the user's own machine, started by the host as a child process. A remote server is a web service that many users reach over the network. Enterprise capabilities like prequal are always remote servers: one deployment, central security, central logging.

04The protocol: JSON-RPC 2.0

MCP messages use JSON-RPC 2.0, a small, old and very simple standard. There are three kinds of message:

KindShapeMeaning
Request{"jsonrpc":"2.0","id":7,"method":"tools/call","params":{…}}Do something and answer me. The id links the answer to the request.
Response{"jsonrpc":"2.0","id":7,"result":{…}} or "error":{…}The answer to request 7.
Notification{"jsonrpc":"2.0","method":"notifications/progress","params":{…}}Information only; no answer expected (no id).

Compare with REST: instead of many URLs and HTTP verbs, everything goes to one URL (for us /mcp) as an HTTP POST, and the method field says what to do.

The methods a tool server deals with (2026-07-28)

MethodPurposeDo we use it?
server/discoverOptional first call: which protocol versions and capabilities the server supports. Servers must implement it.Provided by the SDK
tools/listReturns the tool catalogue: names, descriptions, input and output schemas, annotations.Yes
tools/callRuns one tool with arguments and returns the result.Yes, the main one
resources/list, resources/read, resources/templates/listRead-only content the host can load as context (documents, reference data).Later: disclosures, product terms
prompts/list, prompts/getReusable prompt templates a user can pick.Optional
completion/completeArgument auto-completion in user interfaces.No
subscriptions/listenOne long-lived stream for change notifications (for example "tool list changed").No
tasks/get, tasks/updateLong-running operations, through the official tasks extension.Possibly later

Errors: two different kinds

  • Protocol errors are JSON-RPC error objects: unknown method, malformed request, unsupported protocol version. The model usually never sees these.
  • Tool errors are normal results with isError: true and an explanation in the content. The model reads them and can recover, for example by asking the applicant for missing consent. This is how our server reports business rule violations.

05What a server can offer: tools, resources, prompts

Tools
model-controlled

Actions the model decides to call. Can read or change things. Prequal: get offers, accept offer, get status. Almost all enterprise value is here.

Resources
application-controlled

Read-only content identified by a URI that the host may load into context. Prequal: the soft-inquiry disclosure text, product terms, a glossary of decision reasons.

Prompts
user-controlled

Named, parameterised instructions a person picks from a menu. Prequal: "Run a prequalification for a customer on the phone".

Tools are what leadership means by "exposing our APIs to agents". Resources become useful for compliance content that must be presented exactly. Prompts are a convenience for internal users.

What a tool result can contain

  • content: a list of items (text, images, links to resources). This is what models read today.
  • structuredContent: a JSON value matching the tool's outputSchema, for hosts and programs that want machine-checkable output.
  • isError: true when the call failed in a way the model should read and act on.
  • resultType: "complete" normally, or "input_required" when the server needs more input first (section 08).

06Transports: how the messages travel

TransportHow it worksUse it for

            "io.modelcontextprotocol/clientInfo":{"name":"copilot","version":"…"}}}}

The two new headers matter to us. Apigee or Kong can now apply policy per tool, for example "only the call-centre agent app may call prequal_accept_offer", by reading a header instead of parsing JSON.

07Lifecycle: stateful before, stateless now

The biggest change in the 2026-07-28 specification is that MCP became stateless. Our proof of concept is built on Spring AI 1.1, which speaks the earlier 2025-06-18 version. Both are shown so you can recognise them.

What changed in 2026-07-28 and what it means for us

ChangeBeforeNowImpact on apply-mcp-server
Sessionsinitialize handshake, Mcp-Session-Id headerRemoved. Each request carries version and client info in _meta.Our tools already keep no session state. State lives in explicit ids (prequalId, applicationId), which is exactly the new pattern.
Gateway headersGateway had to parse the bodyMcp-Method and Mcp-Name requiredPer-tool policy in Apigee or Kong becomes simple.
Server-to-client requestsServer opened requests to the client (elicitation, sampling)Multi round-trip requests (MRTR)Use MRTR for accept confirmation once supported (section 08).
List cachingNonettlMs, cacheScope, deterministic orderHosts can cache our tool list; keep order stable.
Long-running workExperimental tasks in coreOfficial tasks extension with pollingUseful if an application decision ever takes minutes.
DeprecatedRoots, Sampling, Logging; HTTP+SSE; Dynamic Client RegistrationKept for at least 12 months, then removedWe use none of them.
AuthorizationOAuth 2.1 profileTightened: issuer validation (RFC 9207), Client ID Metadata Documents preferredCovered in document 2.

Version note for our stack. Spring AI 1.1 on Spring Boot 3.5 speaks 2025-06-18. Spring AI 2.0 (generally available June 2026, Spring Boot 4, MCP Java SDK 2.0) is the line to move to. Its documentation offers a STATELESS server protocol mode. Confirm 2026-07-28 support in the Java SDK release notes before committing to a date. Clients negotiate the protocol version, so a 2025-06-18 server keeps working with current hosts during the transition.

Spring AI already lets you choose spring.ai.mcp.server.protocol: STATELESS instead of STREAMABLE. For a PCF deployment with several instances behind a round-robin router, stateless is the right choice even before the 2026 protocol, because no instance needs to remember a session.

08Asking the person mid-call: multi round-trip requests

Sometimes a tool needs input from the person before it can finish: a confirmation, a missing value, a disclosure acknowledgement. In 2026-07-28 this works as a multi round-trip request (MRTR): the server returns resultType: "input_required" with the questions, the host asks the person, and the client sends the original request again with the answers.

Our proof of concept uses an applicantConfirmed argument because MRTR needs both a 2026-07-28 server SDK and host support. Moving accept confirmation to MRTR is on the roadmap (document 4). Keep the server-side check either way.

09Extensions and the feature lifecycle

The core protocol is deliberately small. Optional capabilities are published as extensions that clients and servers advertise in their capabilities. Three official extensions matter for an enterprise:

ExtensionWhat it addsRelevance
io.modelcontextprotocol/tasksLong-running operations: the server returns a task handle; the client polls with tasks/get and can send input with tasks/update.If a decision or document check takes minutes.
MCP AppsServers can provide interactive user interface components the host renders.Possibly for displaying offers and disclosures richly. Not needed now.
Enterprise-Managed Authorization (EMA)The corporate identity provider decides centrally which employees may use which MCP servers, without per-server consent screens.High. Covered in document 2.

Since 2026-07-28 the specification has a formal lifecycle: features move from Active to Deprecated to Removed, with at least twelve months in Deprecated. This gives an enterprise a predictable upgrade window.

10Anatomy of a good enterprise tool

ONE ENTRY FROM tools/list
{
  "name": "prequal_accept_offer",                 // stable id, product_action, never renamed
  "title": "Accept a prequalified credit card offer", // for people
  "description": "Accept one prequalified credit card offer and create
     a credit card application. This cannot be undone. Only call this after …
     Idempotency: … retry with the SAME idempotencyKey …",   // for the model: what, when, prerequisites, retry rule
  "inputSchema": { "type": "object", "properties": { … }, "required": [ … ] },
  "outputSchema": { … },                               // optional: shape of structuredContent
  "annotations": { "readOnlyHint": false, "destructiveHint": true,
                   "idempotentHint": true, "openWorldHint": false }
}

Rules we follow (and why)

RuleWhy
One tool per business task, not per endpointFewer, clearer choices for the model. Our three tools map to the three steps of prequal.
Name as product_action in snake_case, never renameNames are an interface. Renaming breaks agents and prompts that rely on them.
Description says what, when, prerequisites, what comes next, retry ruleThe model has no other source. Write for a reader with zero Synchrony knowledge.
Flat inputs with constraints in the schemaModels fill flat objects more reliably. Formats and enums prevent many errors.
Plain values in results, no internal codesThe model would guess what A1 means and could tell an applicant something wrong.
A nextStep in every resultGuides the model through the business process without the host knowing it.
Errors as instructions"Consent missing; ask the applicant…" lets the model recover correctly.
Annotations set honestlyHosts use destructiveHint and readOnlyHint to decide when to ask the person for approval. They are hints, not security.
Rules enforced in codeA description guides a well-behaved model; code stops a misled one.
Minimal data out, no PII echoedResults go into the model's context and possibly logs at the host.
State through explicit ids bound to the callerRequired by the stateless protocol; binding prevents one user using another user's id.

12SDKs, languages and governance

MCP is language-neutral. Official SDKs exist for TypeScript, Python, Go, C#, Java, Kotlin, Rust and others. The MCP project's 2026-07-28 announcement lists TypeScript, Python, Go and C# as Tier 1 SDKs that supported the new version at release. The Java SDK is built together with the Spring team and is integrated into Spring AI.

OptionStrengthsFor us
Java: Spring AI MCP serverAnnotation-based tools (@McpTool), Spring Security, Actuator, our existing build, test and deployment pipelineChosen. Document 3 explains why.
Python: official SDK (FastMCP style)Fastest to prototype; largest example baseGood for learning; would be a new runtime to support on PCF
TypeScript: official SDKReference implementation; newest features firstNew runtime for the team
No code: gateway-generated (Apigee MCP proxy, Kong)Turns OpenAPI operations into toolsFor simple read-only tools later

Who owns the standard

Anthropic created MCP in November 2024 and in December 2025 donated it to the Agentic AI Foundation under the Linux Foundation, with other large AI and technology companies as members. Changes go through public specification enhancement proposals (SEPs). For an enterprise this means MCP is an open, vendor-neutral standard, not a single vendor's product.

VersionHeadline
2024-11-05First release: tools, resources, prompts; stdio and HTTP+SSE
2025-03-26Streamable HTTP; first OAuth 2.1 authorization; tool annotations
2025-06-18Authorization reworked: server as OAuth resource server, protected resource metadata, resource indicators; structured tool output; elicitation
2025-11-25Client ID Metadata Documents; experimental tasks; URL-mode elicitation
2026-07-28Stateless core; Mcp-Method/Mcp-Name headers; MRTR; extensions framework; deprecation policy

13How to build any MCP server: the recipe

  1. Pick the business tasksList what an agent should be able to do, in business words. Group endpoints into tasks. Mark each task read-only or state-changing.
  2. Write the tool contract before codeName, description, inputs with constraints, outputs, errors, retry rule, prerequisites. Review it with someone who does not know the API.
  3. Build the adapterA client for the existing APIs behind an interface, with a deterministic mock for development.
  4. Build the tool layerValidation, rules enforced in code, translation of codes, minimal results, a next step in each result.
  5. Expose over Streamable HTTPOne endpoint, stateless, behind the gateway.
  6. Secure itOAuth bearer tokens validated at the gateway and the server; per-tool authorization; no token passthrough (document 2).
  7. Test at three levelsUnit and contract tests; protocol tests with an MCP client; conversation tests with a real model.
  8. Operate itLogs without PII, traces across gateway, server and APIs, metrics per tool, alerting.

Our repository already implements steps 1 to 5 and 7 for prequal with a mock backend. Documents 2 to 4 cover security, production architecture, and the path from here to production.

14Glossary

LLM
Large language model: the AI that reads and writes text.
Agent
A model running in a loop with tools, able to take several steps towards a goal.
Host
The application containing the model, for example Copilot in IntelliJ.
MCP client
The part of the host that connects to one MCP server.
MCP server
The service that publishes and executes tools. What we build.
Tool
A named action with a description and input schema that a model can call.
Resource
Read-only content with a URI that a host can load.
Prompt
A reusable instruction template offered by a server.
Context window
The text a model can see at once: conversation, tool descriptions, tool results.
JSON-RPC 2.0
The message format of MCP.
Streamable HTTP
The remote transport: HTTP POST to one endpoint.
MRTR
Multi round-trip request: the server returns input_required and the client retries with answers.
Extension
An optional, separately versioned addition to the protocol.
Prompt injection
Text that tries to make a model follow an attacker's instructions instead of the user's.
